# Verification

Run `pnpm verify` from the repository root with the pinned Node and pnpm versions. It stops on the first failure, in this order:

| Command | What it proves |
| --- | --- |
| `pnpm verify:style` | Biome formatting, recommended lint rules, and import order. |
| `pnpm verify:ui` | The web app composes shadcn/ui with theme tokens, static known classes, and the approved component composition rules. |
| `pnpm verify:types` | TypeScript checks the app, contract, tooling, and tests. |
| `pnpm verify:complexity` | Classic cyclomatic complexity is at most eight for each authored function. |
| `pnpm verify:migrations` | D1 migrations replay on an empty, already-migrated, and populated previous schema; drift, edited published migrations, and explicit transactions fail. |
| `pnpm test:coverage` | Vitest tests Node policies, the built Worker under workerd, the CLI as real Node processes with private Secret Service, and the web app in Chromium; then `e2e run --strict-cache` runs the deterministic owner journey with zero retries. |
| `pnpm verify:crap` | Complete, current execution evidence gives each scoped function a CRAP score at most eight. |
| `pnpm build` | Vite builds the SPA and esbuild bundles the Worker for workerd and the CLI for Node 26. |
| `pnpm verify:load-time` | The production first screens and navigation fit fixed load-time budgets on a 4G phone network. |

`pnpm test` builds the production target before running Vitest. A narrow run such as `pnpm test tests/worker.test.ts` uses the same HTTP target. After `pnpm test`, `pnpm test:journey` runs the journey against that target, with the same allowlisted environment and host-resource tripwire; strict cache replay and zero retries stay mandatory. `pnpm test:coverage` prepares its own separately instrumented build and needs no prior build. The complete test, coverage, verification, and load-time commands also keep their build, E2E, and browser subprocesses inside the isolation lifecycle.

All local identities, signing keys, and issuer responses are synthetic. Linux CLI tests require Node 26.10, `bubblewrap` (`bwrap`), `dbus-run-session`, `dbus-send`, `gnome-keyring-daemon`, and `secret-tool`. CI installs `bubblewrap`, `gnome-keyring`, `libsecret-tools`, and `dbus` in the test jobs. Each CLI fixture creates private HOME/XDG directories, including XDG_DATA_HOME for the encrypted keyring files, and a private bus with no service activation directories, asserts that its address differs from the inherited bus, and unlocks a real isolated keyring before launching the CLI. The daemon runs with `--foreground` alongside `--unlock --components=secrets`: the fixture waits for stdout EOF after initialization, then requires a real store/lookup/clear probe. The background launcher exits before initialization, so its exit is insufficient. Daemon streams are discarded. PATH shims record opener URLs and secret-tool argv, then delegate to the real binaries; the bus-identity shim delegates to the real dbus-send; values travel only over stdin. Missing-service tests deliberately omit the daemon. Fixtures reject bus overrides before every child, clean failed setup, stop the owned daemon and children before removing HOME, and kill any remaining private process group; shutdown has a bounded force-kill fallback. A concurrent fixture regression proves that inherited XDG data remains untouched. The runtime reads asset routing and compatibility settings from `wrangler.jsonc`, binds only to `127.0.0.1`, and takes explicit test bindings. Test port leases stay above Fetch's blocked-port range and outside Linux's ephemeral range. No test reads production credentials or contacts a Cloudflare account. Coverage endpoints and counters exist only in the test build.

The macOS CLI acceptance runs only on a disposable GitHub-hosted `macos-latest` runner, with `pnpm test:coverage --macos-cli`. Only that workflow job sets the allowlisted `NOOK_TEST_MACOS_KEYCHAIN_BOOTSTRAP=github-hosted` opt-in. Without it, fixture setup fails with a message pointing to [#40](https://github.com/taecontrol/nook/issues/40); `CI=true` alone never enables creation. Local creation is forbidden on the owner's Mac. Each fixture creates and resolves a fresh temporary HOME, rejects the real owner HOME, and requires an empty user search list and an absent login keychain before creating `Library/Keychains/login.keychain-db` with an absolute path. Immediately after creation, both login and default keychain must resolve inside HOME before any item command or CLI child. No test changes the search list or default, locks, unlocks, deletes, or moves a keychain. Missing and locked states are reproduced with failing/stalling PATH shims. Every child requires the fixture file to exist and the shims to be first on PATH; `open` never delegates to the real opener. Commands and process groups stop before HOME is removed.

Vitest's global host-resource tripwire runs for `pnpm test`, `pnpm test:coverage`, and `pnpm verify`, including CI shards. It resolves the real owner with `os.userInfo().homedir`, fingerprints entry names and kinds beneath the owner's keyring directories, and preserves an explicit absent state. Existing keyring file sizes and mtimes are not compared: legitimate owner applications refresh stored credentials while verification runs. A Codex OAuth refresh was attributed to such a change during diagnosis. Added or removed entries, changed kinds, and a directory appearing or disappearing still fail. The Nook configuration directory also compares sizes and mtimes. Teardown names the changed resource and entries without exposing contents, detects leftover processes with temporary CLI HOME or a run-owned keyring/bus daemon, kills those processes after checking PID identity, and reports them; it never cleans owner resources.

On macOS, the tripwire observes the owner’s `~/Library/Keychains`, Nook config, and HOME-scoped lock directory. It records only entry names/kinds and the read-only `security list-keychains -d user`, `default-keychain -d user`, and `login-keychain` results before and after. Existing keychain size/mtime refreshes pass; search-list/default/login path changes, entry changes, and Nook config/lock writes fail. Process inspection reads only `ps -axo pid=,ppid=,pgid=,uid=,lstart=,comm=`. macOS fixture hosts and CLI children launch detached into separate process groups; each known member's PID, start time, group, UID, and run root PID are recorded under temporary HOME and shared by the run’s workers. Cleanup requires the same UID, a PID/start identity absent from the baseline, and membership in a verified group or descent from the run. A group is verified only while an unchanged registered member survives; a recycled group number never authorizes a signal. Known inherited children register before their launcher exits, preserving ownership after reparenting. A leftover in a recorded group without a surviving identity fails the check without sending a signal. Arguments and environment text never authorize termination. PID, start time, UID, and group are checked again before termination. Each Keychain fixture also mirrors its CLI and spawned command identities into a private journal. A shared process factory creates a pending marker before launch, verifies the live leader's parent and detached group, and retires the marker after registration. A fast command that already exited retires it only when a complete kernel snapshot contains neither its PID nor any member of its group; no signal is sent. Failed registration or an interrupted launcher leaves the marker, and journal readers reject it by name even when it is a directory or symlink. The fixture's close operation selects only verified groups in its journal, stops adopted children, and waits for their disappearance before removing HOME. It never uses the common runner ancestry to close an individual fixture, and preserves HOME when registration, ownership, or termination cannot be proved. Synthetic tests prove path redirection, metadata exclusion, symlink handling, kernel metadata, adopted descendants, misleading argv/environment values, recycled groups, pending registrations, and baseline preservation.

The Linux observer does not contact D-Bus, including private buses, and has no Secret Service fingerprint. In Ubuntu's systemd 255, `busctl get-property` ignored `--auto-start=no` and activated gnome-keyring, creating the owner keyring directory on a fresh runner. Replacing it with a non-activating `Properties.Get` call was also unsafe: during verification on 2026-10-05 at 10:01:34, the owner's gnome-keyring daemon aborted with SIGABRT in its property handler after a client disconnected, consistent with the observer's short timeout. Even read-only calls can harm the service. The filesystem observer cannot detect changes to items inside an existing keyring file; prevention comes from the allowlisted child environments, explicitly unavailable default bus, and private-bus fixtures. A shared bubblewrap launcher now prevents private-keyring hosts, CLI processes, their daemons and shims, and activation-bus daemons and controls from reaching those filesystem resources.

The test runner and every host-touching child use environments built from an explicit allowlist, with temporary HOME and all XDG directories. Parent bus, keyring, credential, display, and arbitrary environment variables do not propagate. An explicit unavailable bus address prevents implicit discovery of the owner's bus; private-keyring fixtures replace it with their own bus. The owner's HOME is rejected as a temporary HOME. `NODE_OPTIONS` is accepted only as an explicit fixture injection; coverage output paths are supplied explicitly. Directory overrides must stay inside temporary HOME, except the documented CLI config fallback. Chromium gets a fresh temporary profile, `--password-store=basic`, `--use-mock-keychain`, and no owner bus. The E2E engine runs under the same isolated caller environment and uses Playwright's basic/mock defaults. Regression tests inspect the real CLI, daemon and browser launch environments, deliberately mutate a fake owner tree to prove the tripwire fails while same-name keyring metadata refreshes do not, prove filesystem observation cannot activate a reachable synthetic service, and terminate a synthetic orphan.

Every host-touching fixture starts through `tests/support/sandbox.ts`, with no unsandboxed fallback. The sandbox uses `--unshare-user --unshare-pid --unshare-ipc --die-with-parent --new-session --clearenv`, supported by bubblewrap 0.9.0 and later. It sets exactly the allowlisted `testEnvironment` output; `/usr/bin/env --unset=PWD` removes the variable bubblewrap adds before executing the child. Read-only mounts at identical host paths are `/usr`, `/etc`, the resolved Node installation directory, and the repository; `/bin`, `/lib`, `/lib64`, and `/sbin` link into `/usr`. `/proc` and `/dev` are private pseudo-filesystems. `/tmp`, `/home`, and `/run` are empty tmpfs mounts, with an empty owner HOME and `/run/user/<uid>`; only parents of allowlisted mounts appear beneath them. The fixture HOME is bound read-write after the repository, including when `tempRoot` sits within it. Only coverage runs additionally bind `.local/verification/coverage` read-write for CLI execution evidence. Closing the fixture stops its sandbox process group; the PID namespace and `--die-with-parent` stop remaining descendants even after forced termination.

On Ubuntu 24.04 with restricted unprivileged user namespaces, load the versioned [nook-bwrap AppArmor profile](../../.github/apparmor/nook-bwrap) after installing bubblewrap:

```sh
sudo apparmor_parser -r .github/apparmor/nook-bwrap
```

The profile grants `userns` to `/usr/bin/bwrap`; it leaves the runner's global restriction and Chromium's AppArmor policy intact. CI loads it in each test shard before `pnpm test:coverage`. Missing bubblewrap or a denied UID map fails setup with installation/profile instructions and removes the fixture HOME; tests never skip or retry outside the sandbox.

The network namespace is shared so the CLI reaches workerd at its actual `127.0.0.1:<port>` origin and retains its abstract-socket session-lock semantics. Consequently, host abstract Unix sockets remain reachable. Neither the observed Omarchy owner bus nor CI uses an abstract D-Bus address; filesystem session-bus sockets remain absent. This is a deliberate limit of the isolation boundary.

Escape probes first use only `stat`/`statfs` metadata to require absent owner keyring/configuration/bus paths and tmpfs mount parents with no unexpected entries. [Linux tmpfs directory sizes](https://github.com/torvalds/linux/blob/master/mm/shmem.c) account for the two dot entries and 20 bytes per child, allowing that check without listing owner paths. A failed gate exits before any write or connection. Positive probes write only to the sandbox's tmpfs and read only a synthetic unbound host sentinel; negative controls expose a synthetic owner tree inside bound fixture HOME and require it to remain unchanged. The existing filesystem tripwire and orphan detector remain active on every run.

Run independent test and verification commands sequentially on the same machine. On Linux, the orphan detector collects processes with any `/tmp/nook-cli-*` HOME, including another invocation's processes, and terminates them at teardown. On macOS, each run tracks its own groups, UID, baseline, and process ancestry. Vitest workers within one invocation share that lifecycle; CI shards use separate machines.

## Coverage and CRAP

The coverage inventory starts from original TypeScript and TSX, including files no test imports. [coverage.config.json](../../coverage.config.json) defines the scope: CLI, Worker, web, contract, and the Node policy modules in `scripts/lib`. Script entry points are orchestration and are covered by command and workflow acceptance checks; every authored script function still enters the complexity check. Unconfigured executable extensions fail inventory validation.

Unchanged CLI-generated shadcn components and their mobile hook are recorded by SHA-256 in [generated-components.json](generated-components.json). Changing one fails the inventory until it enters authored scope. The generated primitives retain their standard internal styles; authored composition still obeys all six UI rules. Declarations and dependencies do not enter authored coverage.

The grant checklist uses the CLI-generated shadcn Checkbox with the already installed Radix dependency. ItemDescription is authored scope: its `truncate` prop defaults to the original two-line presentation, while Machines disables truncation to display the complete grant. Neither the UI rules nor coverage gates exempt that change.

Istanbul instruments original sources before Node execution, CLI child-process bundling, Worker bundling, and browser compilation. The CLI test entry records its counters at process exit without recording arguments, environment values, or command output. The CLI execution seam is required whenever CLI sources enter the inventory. Coverage artifacts in `.local/verification/coverage/` include a zero baseline, each seam's loaded-module hashes and counters, and a manifest of artifact hashes. Source identity includes app, contract, tooling, tests, documentation, workflows, configuration, and the lockfile, using repository-relative paths so a clean export and a CI shard agree.

CRAP rejects a missing baseline or seam, empty or unexecuted seam observations, stale source, unknown modules, incompatible counter maps or shapes, and altered artifacts. Coverage is the fraction of the function's own statements executed, excluding nested functions. A statement-free function uses its function counter. Classic complexity counts decisions independently for each function. The score is `complexity² × (1 − coverage)³ + complexity`.

CI runs the five static commands, three `pnpm test:coverage --shard=I/3` jobs, a macOS CLI coverage job, and a final job. Each platform job uploads its manifest and artifacts; the final job requires the distinct indexes `1/3`, `2/3`, `3/3`, and `macos`, identical source identities and baselines, and intact artifact hashes before CRAP, build, and the load-time check. The timing stage runs alone after test jobs finish. It needs no Cloudflare secrets.

## Migrations

`migrations/NNNN_name.sql` files are applied in order using Wrangler's SQL splitter and one atomic D1 batch per file, including its `d1_migrations` record. `migrations/schema.sql` is a snapshot, not a migration. The D1 binding's `migrations_pattern` selects only numbered files; a local Wrangler acceptance test proves that it excludes the snapshot and preserves replay. Verification uses fresh Miniflare databases, checks an idempotent replay, and applies the latest file to the previous schema containing a sentinel bucket. Both final normalized schemas must match the snapshot, and the sentinel must remain unchanged. A second migration enforces the reserved `me` invariant at the database boundary.

Fetch `origin/main` before verification: a migration present there cannot change or disappear. SQL errors, schema drift, and `BEGIN TRANSACTION` fail the gate. Deployment relies on the commit's successful Verify run instead of repeating it, builds, creates the named database if missing, applies remote migrations, then deploys the Worker. Production acceptance remains an owner step described in [deployment.md](../deployment.md).

`tests/cli-release.test.ts` proves that `nook version` prints `{"version":"X.Y.Z"}` from `apps/cli/package.json`, the only version source, and that the CLI bundle runs as a Node single executable with no Node on `PATH`. It runs in the Linux shards and the macOS CLI job. Verify's `linux-binary` job (Linux x64) and the `macos-cli` job (macOS arm64) also run `node scripts/release/binary.ts`, the release packaging step, which checks `nook version` under `env -i PATH=/usr/bin:/bin`. `tests/release-archive.test.ts` extracts a release archive with the system `tar` and requires exactly the executable, byte for byte, beside a `sha256sum` checksum. `tests/release-rollback.test.ts` runs the release workflow's own publish and unpublish scripts against a local bare repository with stub `gh` and `ssh`: a failed release deletes the tag it pushed and the release it created, and neither script passes the deploy key in an argument list. The release workflow's own checks are described in [releasing](../releasing.md).
